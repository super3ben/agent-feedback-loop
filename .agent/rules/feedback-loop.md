# Feedback Loop 项目规则

本文件记录本项目特有的、由反馈反思得出的可执行规则。

## Verification Honesty（验证诚实）

不得把单元测试或安装接线检查等同于端到端验证。

在向用户声称「验证通过 / 全部通过 / 已验证」之前,必须:

1. 显式区分两类验证并分别标注状态:
   - **机制层**:单元测试、JSON 形状、doctor/healthy、安装与幂等接线。
   - **端到端层**:在真实 Codex/Claude/Gemini 会话里发强触发,确认 hook 真被 CLI 调用、
     `additionalContext` 真进入模型上下文、模型真的开始反思。
2. 明确列出「实际做了哪些验证项」和「哪些没做 / 无法做」,不得用机制层证据隐含端到端结论。
3. 对本项目这类「价值 = 注入指令真正进入模型上下文并改变模型行为」的工具,
   doctor/healthy 与形状检查只能证明「接线正确」,不能证明「功能生效」。
4. 端到端未做或受环境限制无法做时,用限定措辞,例如:
   「机制层已验证通过;端到端尚未验证,原因是 ___。」不得使用无限定的「全部验证通过」。

反例(避免过度收窄):若用户只要求跑单元测试,如实声明「单元测试通过」即可,不必扩大范围。

## No False Positives in Test Assertions（测试判据不得假阳性）

用 grep/字符串匹配判断「模型是否收到注入内容」时,判断范围不得混入命令自身的字面量。

- 曾犯:`grep 反馈反思已触发` 同时扫了 stdout 和「我自己 shell 命令里的中文」,得到假阳性,差点据此声称验证通过。
- 要求:只对**被测程序的真实输出文件**做断言;命令里若出现待匹配字符串,必须隔离(写独立文件再 grep,或用探针留痕)。
- 一条 grep 命中不足以下结论;需有独立的、不依赖命令字面量的证据(如 hook 留痕探针)。

## Never Copy Auth Credentials Across CODEX_HOME（不要跨 CODEX_HOME 复制凭据）

做 codex 隔离测试时,**禁止**复制 `~/.codex/auth.json` 到临时 home。

- 曾犯:为隔离测试把 `auth.json` 复制进临时 `CODEX_HOME`,OpenAI 检测到同一 token 多处使用,
  触发 `token_invalidated` / `refresh_token_invalidated`,把用户**真实**的 codex 登录也弄失效了。
- 正确做法:用真实 `~/.codex`(凭据/登录都在那),仅用命令行 `-c hooks.UserPromptSubmit...` 临时覆盖 hook
  指向待测脚本,既不写用户 `config.toml`,也不动凭据。
- 任何「复制凭据」「在两个目录间共享 token」的隔离测法都禁止。

## Verify the Premise Before Building on It（先验证前提,再展开）

涉及「判断某个外部来源 / 平台 / 出处 / 归属」等**可直接查证的事实前提**时,
若无直接证据,禁止凭猜测下结论或据此展开长篇解释。必须先二选一:

1. 看证据:截图/日志/文件就在手边时,直接观察其 UI、措辞、特征自行确认;
2. 问用户:无法从手边证据确认时,用一句话直接询问,不要替用户假定。

- 曾犯:用户发来一张静态截图问「为何反思占用主会话」,agent 在无证据下断定截图来自 Codex,
  并写了整套「Codex 无后台 subagent」的解释;实为 Claude Code,前提错误导致整段解释作废。
- 关键判据:前提是否「可观察 / 可询问」?可——必须先查证;猜测即过失。

反例(避免过度收窄):对**无法查证**的事项(如用户私有意图、外部不可见状态),
可在显式标注「假设」的前提下给出有条件的答复,不要求停下来反复确认。

## Background Reflection First（反馈反思优先后台执行）

修改 hook / feedback-loop / 自动反思机制时,必须把目标层级先判定清楚:
个人用户级、项目模板级、还是单一项目级。涉及“每个项目”“project 级别”
或“个人用户级别”的表达,默认做可复用机制。

当 feedback-loop 识别到需要反思的用户反馈时:

1. 若目标平台提供真正后台 subagent 能力(例如 Claude Code Task、Codex multi-agent),
   必须自动委托后台 subagent 生成结构化回执,主会话不得执行完整反思。
2. 主会话不得粘贴完整反思报告,不得把“是否要启动后台反思”交回用户确认；只负责一次性
   `reviewer-submit`。
3. 报告、lesson、application/delivery/effectiveness receipt 以用户级事务数据库为真源；自动反思
   不得修改项目 Git 中的 `.agent/reflections/` 或 `.agent/rules/feedback-loop.md`。
4. 若当前平台没有真正后台 subagent,job 必须保持 pending 并报告 `reviewer_unavailable`；禁止主会话
   fallback 代写。没有显式释放 API 时只记录能力限制,不得伪造已释放。

反例(避免过度收窄):在不提供后台 subagent 的运行时中,不得伪造后台执行,也不得由当前 agent
代写回执；应保留待处理证据,等待可用 reviewer。

## Prospective Constraints Are Not Feedback（前瞻性任务约束不是反馈）

反思触发判定(语义 gate 及任何后续分类器)必须区分两类消息,只有前者触发反思:

1. **回顾性纠正/不满**:指向 agent **已经产出**的内容或**已经发生**的行为
   (「怎么又…」「为什么还…」「上次就说过」「不要再犯」「重做」),或明确表达不满情绪。
2. **前瞻性任务约束**:布置新任务时附带的质量/格式/内容要求
   (「记得一定要有事件依据」「不要全是宽泛的总结」「必须包含…」「注意…」)。
   这类消息即使包含「一定要…」「不要…」句式,也是普通指令,**不得**触发反思。

修改或编写 gate 提示词(如 `trigger-rules.sh` 的 `agent_feedback_gate_message`)时:

- 触发条件不得只列正例;必须同时给出排除条款与至少一组正/反对照示例
  (「不要再犯」=纠错 vs 「不要全是宽泛总结」=新任务约束)。
- 「要求未来防复发规则」这一触发项仅限用户明确针对 agent 过失要求立规,
  不包括对交付物本身的要求。
- 拿不准时宁可漏报不误报:反思机制的价值在低噪音,普通指令触发反思即是本机制自身的过失。

反例(避免过度收窄):若用户在布置新任务的同一条消息里**同时**指涉既往缺陷
(「上次总结太宽泛了,这次一定要有事件依据」),仍属回顾性纠正,应当触发反思。

## Explicit Stop Is a Terminal Boundary（明确收尾后立即终止探索）

当用户明确要求停止继续检查/分析、不要再调用工具并基于已有证据返回结果时，当前 agent
必须把该消息视为本轮工作的终止边界：立即停止新的工具调用、文件读取和扩展性分析，使用已经
收集的证据完成当前输出；若已有子 agent 或同步命令正在运行，先中止或等待其有界退出，再返回
结果。该要求在同一评审流程中被重复提出时，属于对既有行为的回顾性纠正，必须优先于继续提高
结论完整度的默认倾向。只有用户随后明确授权继续检查，才能重新开始取证。

## Elicited Corrections Are Not Feedback（被征求的纠正不是反馈）

反馈判定不得只看**消息文本特征**(回顾性措辞、可逐字引用、有所指产出);必须先做**语境归属检查**:
该纠正产生于谁发起的流程环节?

1. agent 主动发起的征求环节(澄清提问、草稿/设计文档评审、计划确认、预览确认)内,
   用户的答复与纠正是被征求的评审意见,**一律不算反馈**——即使用户逐字引用草稿原文并指出其错误。
   例外(此时算反馈):同一纠正被跨轮重复;用户对流程本身表达不满(「又没理解」「怎么还要我说一遍」);
   被纠正的产物已定稿/交付而非正在共审。
2. 修改判定标准(prompt / trigger-rules / 任何分类器)时,新增或依赖一条正向判据前必须自问:
   「什么**语境**会让完全满足该判据的消息仍然不是反馈?」答案是一类语境时,
   必须把该语境作为独立判定维度写入标准,禁止只往排除词表里加一条措辞。
3. 同类误报第二次出现即视为「维度缺失」而非「枚举不全」,禁止再用同层排除条款打补丁。

- 曾犯:批量评审 subagent 把澄清环节里「引用设计文档草稿行 + 指出权重已实现」的消息判为反馈,
  归档报告并追加规则;该消息满足当时全部文本判据,缺的是语境维度。
  (见 20260708-161315 反思报告;父类首现见 20260703-171840)

反例(避免过度收窄):用户**自发**(非被征求)指出已交付产物的错误,即使发生在讨论中途,仍是反馈;
本规则只豁免「agent 请来的评审」,不豁免一切讨论期纠正。

## Completion Includes Value and Clean State（完成判据必须覆盖价值与干净状态）

本仓库改动反思机制(prompt / hook / 规则模板)时,不得把「可见形式产物齐全」
(报告文件存在、字段填齐、回执行输出、不刷屏)当作反思流程的完成判据。完成判据必须同时包含:

1. **价值层验收**:反思报告须满足 `prompts/reflection-agent.md` › Analysis Depth 的三步
   (5 Whys 下探到过程/假设层 → 类别抽象 → 可复用方法改进);
   自检问题是「这份报告是否会改变 agent 对一整类未来任务的做法?」,达不到即为缺陷。
   任何对反思机制的形式层优化(降打扰、改触发、改落地方式)不得削弱该深度契约。
2. **后续会话消费**:学习闭环必须明确并验证「生成 → 持久化 → 活动 projection → 检索/注入 →
   delivery observation → 复发 effectiveness」路径。规则只写入 Markdown、但普通后续会话没有
   application/delivery receipt 时,不得声称该规则会改善后续会话。严重度、责任或类别字段若用于驱动行为,
   必须明确映射到分析深度、升级范围、规则目标或验证要求;仅记录不执行时须明确说明。
3. **资源回收**:任何派生进程/子 shell/subagent 的流程,「结束」定义为
   「产物落地 **且** 无遗留运行中的子进程」;取证命令一律同步、有界、跑一次。
   遗留挂起的 shell 本身即 agent_fault。

- 曾犯:多轮迭代只修形式层(误触发/刷屏/确认),反思退化成「复述 + 窄禁令」,
  用户评价「完全没用」;同期反思流程跑完后 shell 一直挂着无人回收。
  (见 20260708-143832 反思报告)

反例(避免过度收窄):正常开发任务中的后台进程(dev server、长时测试)不受第 3 条限制,
该条只约束反思/评审类流程;第 1 条也不要求对「无真实反馈」的批量评审写深度报告——
一行「reviewed N entries, none are feedback」即是正确产出。

## Audit Requirement, Delivery, and Evidence Before 5 Whys（先审计验收闭环,再做因果分析）

对指向既有任务结果的真实反馈,反思 agent 在选择问题框架和开始 5 Whys 前,必须先逐项建立:

1. 用户逐字提出的要求/验收条件;
2. 既有 agent 宣告完成的具体交付;
3. 宣告完成当时实际给出的直接验证证据;
4. 缺失或直到用户重复后才补出的验收项。

若用户明确指出「之前会话没达到要求」,只有上述审计证明每个验收条件当时都已有直接证据,
才可把问题收窄为措辞、排序或用户误解;否则 5 Whys 必须从未闭环的交付/验证项开始。
正向能力要求必须有正向路径证据,失败/降级样本不能替代成功路径验收,后续补出的证据也不能
倒推此前交付已经达标。

完成 5 Whys 后必须反查第一层:它解释的是「既有产出为什么未满足原始验收条件」,
还是仅解释「用户为什么再次发言」。若是后者,说明问题框架未经验证,必须重新审计后再分析。

- 曾犯:上一份反思把「完整 URL 正向预览能力在第一次交付中没有证据闭环」收窄为
  「当前数据说明放在前面、主线修复被称为顺手」,报告字段和 5 Whys 齐全却漏掉实质交付缺口,
  用户评价反思「就是走个过场」。(见 `20260713-105532-reflection-missed-delivery-gap.md`)

反例(避免过度收窄):若既有交付确有逐项直接证据,用户只是忽略了已经清楚呈现的结果,
可以据证据判为 `user_misunderstanding`;本规则不要求为了迎合不满而虚构 agent_fault。

### reflection-context-ineffective (10×, Major)

**何时适用：**
- 当任务涉及「索引内容修完了，端到端验证、有自己测过吗，效果达到预期要求了吗，还是说改了还是没起到、用户此前回「都做了」、要求落地从 agent 记忆研究借来的四件改动、agent 在 07:3」时，或用户以相近说法指出同类问题时

用户此前回「都做了」，要求落地从 agent 记忆研究借来的四件改动。agent 在 07:32 交付称「索引内容修完了，端到端验证」…

**Do not repeat this mistake:**
- 收到用户的明确范围、能力声明或否定性反馈时，agent 的第一反应是去核查、去执行，而不是先反驳或把活推回用户；事后承认不能替代第一时间做对。
- 当同类问题第二次出现时，把它当作已承诺的 would_qualify_if 已被命中，必须沉淀为反思或规则，而不是再次以相同理由拒绝。

### platform-formula-syntax-support (7×, Major)

**何时适用：**
- 用户说类似「用户在同花顺「一句话选股」跑超卖策略，连续多轮反馈选到 0 只，本次追问「现在是什么问题导致我同花顺选不出来？没看到原因」」时

用户在同花顺「一句话选股」跑超卖策略，连续多轮反馈选到 0 只，本次追问「现在是什么问题导致我同花顺选不出来？没看到原因」…

**Do not repeat this mistake:**
- 以用户的明确反馈和 agent 首次交付为判定依据，逐项核对用户要求与首次交付，记录当时已发生的错误；将后续纠正单独记录，不用它撤销首次错误的沉淀资格。
- 对事后纠正、未部署、用户转述或前瞻建议逐项区分已发生的错误与尚未发生的风险；用户已明确反馈且首次交付已做错的部分，写入反思或规则。
- 同类问题第二次出现时，对照此前拒绝记录中的附加条件；已满足条件的，直接沉淀对应反思或规则，不再重复拒绝或追加门槛。

### backtest-calculation-metric-validity (7×, Major)

**何时适用：**
- 准备比较或推荐 S3 策略次日买入时机规则的 C/D/E 版本，并用总收益排序时
- 分析 S3 策略次日买入规则的收益或止损时，用户提到关注优化亏损、上涨不可控，或要求按 T+1 重新计算时
- 处理 S3 策略次日买入规则时，准备依据当天买入后当天止损的假设进行计算或比较时

用户在迭代S3策略次日买入时机规则（C/D/E对比）时，agent交付了完整的五版规则对比分析，以总收益为主要排序依据（D版+332.4%最高，E版+280.6%推荐）。用户随后反馈两个问题：(1)自己关注的是优化亏损而非盈利…

**Do not repeat this mistake:**
- 按用户关注的亏损优化目标比较 C/D/E 规则；将亏损指标作为主要排序依据，并单独报告总收益。
- 计算次日买入规则时落实 T+1 约束：买入当日不得计为可止损，按下一可交易日及之后的实际可执行时点重算止损与结果。

### design-phase-generation-counting (7×, Major)

**何时适用：**
- 用户说 guard 经常误报、频繁阻塞正常修复，准备要求关闭或放宽守卫之前。

用户在 agent 宣称「现在已经修好了」之后回复：「guard暂时先关了吧，很多时候发现阻塞处比正常修复误触发的次数多，经常会误报」——即误报依旧频繁，被拦次数多于真正需要修复的情况，用户不再要求继续调优而是要求整体关闭守卫…

**Do not repeat this mistake:**
- 先从用户提供的阻塞消息或日志确认触发路径和判定分支，再修改对应实现；若修改路径与触发路径不同，明确列出覆盖差异，不要宣称问题已解决。
- 复现用户报告的被拦操作，并确认原阻塞不再触发后再验收；单元测试通过只作为辅助证据。
- 若豁免依赖外部阶段信号文件，检查这些文件在用户环境中是否存在并会被写入；验证缺失时的默认行为，并说明豁免如何启用。
- 交付时分别说明已验证解决的部分和未覆盖部分；把实现过程中仍出现的 guard 或 grant 阻塞视为验收未通过，先核对触发路径。

### backtest-conclusion-inconsistency (5×, Major)

**何时适用：**
- 用户说类似「用户询问为何此前的策略都没达到50%胜率，或加入-3%/-8%卖出规则后胜率仍只有约30%，要求分析原因」时
- 评审用户对 agent 的明确反馈，判断理解错误、范围做过头或未第一时间回应的问题是否值得沉淀时。
- 评审策略胜率分析：用户询问为何策略没达到50%胜率，或加入-3%/-8%卖出规则后胜率仍约30%，agent 却先整理同花顺一句话选股条件时。
